No browser understands `@screen`, so every one of those blocks parses as an unknown at-rule and is discarded. Verified in the browser: the bundle really does contain the literal string "@screen". Why strip rather than repair. Repairing looked like the obvious move, but the evidence says otherwise on both counts: - 8,974 B of the 9,195 B is `.{bp}:grid-w10` … `.{bp}:grid-w100` (105 utilities across 5 breakpoints) and `.{bp}:ratio-16-9` and friends. Nothing in this site's built output uses a single one of them; inside the theme they appear only in shortcodes/carousel.html, which no page calls. Converting them to valid CSS would turn dead bytes into live-but-unused bytes and save nothing. - The remaining 221 B is `.thumbnail` and `.article`, which DO appear on /tags/core-team/ and /tags/organisation/. But the theme's own markup carries `class="w-full md:w-auto h-full thumbnail …"` and `class="flex flex-wrap md:flex-nowrap article"`, and those md: variants ARE compiled correctly. The @screen rules only restate what the utilities already do, so repairing them is redundant at best and risks disturbing a layout that currently renders correctly. So the whole lot is inert, and 97% of it is for classes nobody uses. It goes. Stripping is also the safe direction: removing rules a browser was already discarding cannot change rendering. The regex handles one level of nesting, which is all these blocks have (an at-rule wrapping flat declaration blocks). Go's RE2 is fine with it. Call this through partialCached so the 125 KB rewrite happens once per build rather than once per page. RE2 has no recursion, so nest the pattern by hand to a fixed depth: body(0) = \{[^{}]*\} body(n) = \{(?:[^{}]*body(n-1))*[^{}]*\} The deepest body in this file measures 4; build to 5 for one level of headroom, and the balance assertion below catches it if the theme is ever rebuilt deeper than that. RE2 is linear-time, so the nested stars carry no backtracking risk. */ -}} {{- $body := `\{[^{}]*\}` -}} {{- range seq 5 -}} {{- $body = printf `\{(?:[^{}]*%s)*[^{}]*\}` $body -}} {{- end -}} {{- /* A rule = selector text (never contains a brace) then one body. An earlier version DID anchor on `(^|\}|\{)` and was wrong — the match consumed the very `}` that the next rule needed as its own anchor, so in any run of adjacent rules to delete, only every second one went. Two things make swallowing the leading selector text safe: - No rule in this file has a selector list mixing a to-delete selector with a to-keep one, so there is never a live selector sitting in front of a matched token. Checked across all 202 rules; if the theme is rebuilt and that stops holding, the coverage script in the commit message is how to notice. - The token must be followed by a `{`, and a declaration block cannot contain one, so a token appearing in a VALUE rather than a selector can never complete a match. `prefers-color-scheme:dark` is untouched.
